# 02 · 账期规则登记册（R1–R12）

每条规则登记：约定、当前实现状态、证据、缺口编号。状态取值：

- ✅ 已实现且有测试/实测证据；
- 🟡 部分实现（路径存在但语义不完整）；
- ❌ 未实现；
- ⚖️ 待产品/财务裁决（open decision，编号 O*，汇总于 [07](07_gap_analysis.md#6-待裁决事项)）。

| 编号 | 规则 | 状态 | 证据 / 当前行为 | 缺口 |
| --- | --- | --- | --- | --- |
| R1 | **身份与去重**：以 `event_id` 为幂等主键；同键重复投递（即使 `ingested_at` 不同）在重放中折叠为一条，并记录重复计数供审计 | ❌ | v1 无 `event_id` 字段；两条相同业务事件被双计。实测：两条 `units=15` → `amount=50.0`（去重目标应为 12.5） | G1 |
| R2 | **追加不可变**：事件存储只追加；任何更正必须以新事件表达，禁止 UPDATE/DELETE 原行 | ❌ | 无存储层，pipeline 每次从输入 JSON 全量重算；不可变性没有强制点 | G14 |
| R3 | **撤回（retraction）**：`event_type=retraction` 且带 `related_event_id` 的事件在重放中排除被引用事件；被引用事件视同 `status=retracted`，从 `total_units`/`event_count` 中剔除 | ❌ | 实测：用量 12 + 撤回事件 → 撤回被当作普通行计数（`event_count=2`），用量照常计费 5.0 | G1 |
| R4 | **迟到事件**：`ingested_at` 晚于账期关账窗口、但 `at` 落在历史账期的事件，按**业务时间 `at`** 归属原账期；触发原发票重算而非计入当期 | ❌ | 引擎不读取任何时间字段，1 月与 2 月事件被合并出一张发票（实测 `total_units=20, amount=25.0`） | G4 |
| R5 | **账期归属**：账期为月历区间 `[start, end]`（含端点）；事件按 `at` 落入且仅落入一个账期；一次重放调用只处理 `billing_period` 声明的窗口 | ❌ | 无 `billing_period` 概念，输入中的全部事件无条件参与计算 | G4 |
| R6 | **跨月切分**：同一账户连续两个月的事件必须产出两张独立发票，各自独立适用免费额度；禁止跨月合并用量 | ❌ | 见 R4 实测，两个月被合并、免费额度只扣一次 | G4、G8 |
| R7 | **合同生效与版本选择**：合同是版本序列；事件适用"满足 `effective_from <= at` 的最新版本"；一次重放中不同事件可能适用不同版本，发票须记录 `applied_contract_version` | ❌ | 只有一份扁平合同，无版本、无生效日；`contract.versions` 输入直接触发 `KeyError` | G6 |
| R8 | **免费额度**：按"账户 × 账期 × 适用合同版本"授予；先对该账期有效用量扣免费额度，剩余才进入阶梯；免费额度不跨月结转、不跨账户共享（结转策略 ⚖️ O1） | 🟡 | v1 `free` 对合并总量扣减一次（fixture：20 单位 − 10 = 10）；方向正确但无账户/账期/版本维度 | G8 |
| R9 | **阶梯价格（边际口径）**：对 `billable_units` 按档边际计费，第 k 档覆盖 `(up_to_{k-1}, up_to_k]`，末档 `up_to=null` 开放；边界值 `units == up_to` 全部按本档计价（样例 02：100 单位 × 2.0 = 200.0，不跨入 1.0 档）。是否提供"封顶价/打包价"档位 ⚖️ O2 | ❌ | 仅单一 `unit_price` 全量乘算；`tiers` 输入触发 `KeyError` | G7 |
| R10 | **退款**：退款是 `event_type=refund` 的原始事件，带货币 `amount` 与 `related_event_id`；只冲减派生金额、**不回冲 `total_units`**；按退款事件自身的 `at` 归属账期；退款超额部分转信用余额而非负账单 ⚖️ O5 | 🟡 | v1 仅有合同级标量 `refund`，可冲减且允许负账单（实测 `amount=-5.0`）；无退款事件、无关联、无用量保护 | G9 |
| R11 | **金额舍入与币种**：金额使用定点十进制（建议 `decimal.Decimal`），每档小计与最终金额按 ROUND_HALF_UP 保留币种小数位；同一发票不得混币种；币种缺省策略 ⚖️ O3 | 🟡 | 使用 `float` + 内置 `round()`（银行家舍入/二进制浮点双重问题），实测 `round(2.675,2)=2.67`；无币种字段 | G13 |
| R12 | **发票冻结与无事件账户**：发票有 `draft → frozen` 生命周期；冻结后重放不得改写，追溯变更只能产出冲红/补差（见 [04](04_contract_retroactive_change.md)）。对 `accounts` 中声明但零有效事件的账户，每期仍产出一张零金额 `draft` 发票，作为"无遗漏"证据 | ❌ | 无发票身份与状态字段；空事件时输出 `account=None, amount=0.0` 的单对象，无法表达"哪个账户无事件" | G10、G11 |

## 规则之间的依赖顺序（重放管线目标形态）

```
输入 JSON
  → schema 版本路由（v1 兼容 / v2-draft）
  → parser 校验（拒绝非法行而非静默丢弃，G12）
  → R1 按 event_id 去重
  → R3 撤回过滤（retraction 排除原事件）
  → 按 account 分组
  → R5/R4 按 at 做账期归属，迟到事件回原账期
  → R7 为每个事件选择合同版本
  → R8 账期内扣免费额度
  → R9 边际阶梯计费
  → R10 退款事件冲减金额
  → R11 十进制舍入
  → R12 组装发票（含无事件零账单），冻结发票走追溯流程
```

## 当前管线的实际形态（`pipeline.run`）

```
输入 JSON → load_records（只查 events 是不是 list）
          → calculate（单行表达式：sum units → 减 free → 乘 unit_price → 减 refund → round2）
          → build_result（平铺信封输出）
```

对照可知：目标管线 10 个节点中当前仅存在"求和、扣免费、乘单价、减标量、舍入、信封"
6 个动作，且每个动作的口径都比目标粗；其余节点与 R1–R12 的差距即 G1–G14。
