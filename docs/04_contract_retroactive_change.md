# 04 · 合同追溯变更的影响范围约定

"追溯变更"指：合同的新版本 `effective_from` 被设置为**早于当前账期**的日期，从而使
历史账期上的事件按新口径重算。本文档规定该类变更必须生成的影响范围（blast radius）
产出物与处理纪律。当前代码对本专题**零实现**（无版本、无发票身份、无状态机，G6/G10/G11），
因此本文档是目标约定 + 验收标准，不是现状描述。

## 1. 触发条件

满足任一即视为追溯变更，必须走本文档流程，不得当作普通发布：

1. 新增合同版本的 `effective_from` 早于今天所在账期的起点；
2. 已存在的合同版本被修改（价格、阶梯、免费额度、币种任一变化）；
3. 合同版本被废止或合并，导致历史事件的版本选择结果（R7）可能改变。

正常的"未来生效新版本"（`effective_from` 晚于当前账期末）不属于追溯变更，按
[05 发布手册](05_release_rollback_runbook.md) 常规发布即可。

## 2. 影响范围计算流程

```
变更提案（contract_id, 旧版本集合, 新版本集合, 生效日）
  │
  1. 圈定受影响事件：
     at >= 新 effective_from 且适用版本选择结果会变化的全部事件
  2. 圈定受影响发票：
     上述事件归属的（账户 × 账期）发票，去重
  3. 对每张受影响发票做双跑重放：
     old_amount = 旧合同口径重算结果（应与冻结值一致，不一致先报数据异常）
     new_amount = 新合同口径重算结果
     delta      = new_amount − old_amount
  4. 按发票状态分流（见第 3 节）
  5. 生成影响范围报告（第 4 节），等待审批
```

## 3. 按发票状态的分流规则（与 R12、兼容矩阵一致）

| 发票状态 | 处理动作 | 禁止动作 |
| --- | --- | --- |
| `draft`（未关账） | 直接以新口径重算覆盖，`invoice_id` 不变，记录修订版本号 | — |
| `frozen`（已关账） | 原发票**一字不动**；按 `delta` 生成补差发票：`delta>0` 补收单，`delta<0` 冲红单/信用余额；补差单引用原 `invoice_id` 与变更提案 ID | 禁止改写、删除、重开冻结发票 |
| 已开票/已报送财务 | 同 frozen，并额外走财务冲销流程（编排层待建，G14） | 禁止绕过财务直接调差 |

边界纪律：

- **免费额度变化**（R8）只改变 `billable_units`，不得修改原始 `total_units`；
- **阶梯变化**（R9）的差额必须能从 `tier_breakdown` 新旧明细逐档解释，禁止只给一个总数；
- **币种变化**属于破坏性变更：历史发票币种不得改写，只能在新生效日之后适用
  （跨币种重算 ⚖️ O7 待裁决）；
- 一次变更提案是**原子**的：要么全部账期重放完成并生成全部补差，要么整体拒绝，
  禁止只重放部分账户/账期。

## 4. 影响范围报告（必备产出物）

每次追溯变更必须产出一份机器可读 + 人工可读的报告，建议结构：

```json
{
  "change_id": "chg-2026-0007",
  "contract_id": "C-A1",
  "effective_from": "2026-01-01",
  "changed_fields": ["tiers", "free_quota"],
  "affected_event_count": 143,
  "affected_invoice_count": 6,
  "affected_periods": ["2026-01", "2026-02"],
  "invoices": [
    {
      "invoice_id": "A1|2026-01",
      "status": "frozen",
      "old_amount": "25.00",
      "new_amount": "20.00",
      "delta": "-5.00",
      "action": "credit_note",
      "applied_versions": {"old": 1, "new": 2}
    }
  ],
  "totals": {"gross_delta": "-30.00", "currency": "USD"},
  "dry_run": true
}
```

字段要求：

- 金额一律字符串定点十进制（呼应 R11，不用 float）；
- `dry_run=true` 的报告只预演不落任何补差；审批后才允许 `dry_run=false` 执行；
- 报告与变更提案、被重放的事件集快照一起归档，保留期与发票相同（R2 审计链）。

## 5. 验收标准（给未来开发的 DoD）

1. 给定样例 `fixtures/examples/` 中的合同，把单价从 2.5 改为 2.0 并追溯到 2026-01-01，
   能输出第 4 节结构的报告，且样例 01 的两张月度发票分别给出 `delta`；
2. 对标记 `frozen` 的发票，重放前后原发票 JSON 字节不变；
3. `draft` 发票重算后 `invoice_id` 稳定、金额更新且修订计数 +1；
4. 无事件账户（样例 04）的零金额发票若额度/价格变化不影响零金额，报告中
   `delta=0.00` 且 `action=noop`，仍需列出以证明已评估；
5. 整批重放保持纯函数确定性（同提案连跑两次，报告字节一致）。

## 6. 与当前代码的差距

| 约定要点 | 当前状态 | 缺口 |
| --- | --- | --- |
| 合同版本与生效日选择 | 无版本字段，`versions` 输入直接 `KeyError` | G6 |
| 发票稳定身份 `invoice_id` | 输出无身份字段，每次运行只是匿名 dict | G10 |
| `draft/frozen` 状态机 | 无状态字段 | G11 |
| 双跑重放与 delta | 引擎单次单口径，无对比能力 | G6、G14 |
| 补差/冲红发票 | 无发票生成层 | G10、G14 |
| 影响范围报告 | 无报告产物（`report.py` 只做单层信封） | G14 |
| 变更审计归档 | 无持久化、无事件存储 | G14 |
